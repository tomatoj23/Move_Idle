# 执法 / 文档体系审计（2026-09-06）

审计对象：AGENTS.md、docs/agents/、CONTEXT.md、docs/design/、schema/、.codebuddy/memory/ 共同构成的「让 LLM 少踩坑」机制。
审计问题：①每会话都能被看到 ②遇问题必做 ③解决后记到该记的地方 ④教训真能防重踩。
性质：**取证式**，不是阅读式。本页只记录证据与判决，不含整改（整改待拍板后另动）。

## 0. 取证方法与边界

| 手段 | 做法 | 覆盖 |

| 静态盘点 | 全库 md 体积 / 职责 / 入仓状态 / 引用关系 | 全量 |

| Runbook B（变体） | 日志每条「已完成 / 票已闭 / CI 绿」声称 ↔ `git log` / `gh issue list` 实据 | 声称 = 实做 |
| Runbook C（变体） | 逐条比对 54 条教训是否回流到仓库规则文档 | 沉淀完整性 |

**边界（影响结论可信度，先声明）**：无会话导出 JSON，Runbook B 退化为「日志 ↔ git/gh」；探针子代理无网络无写权限，只能做评审 / 问答题，观测不到「落码前核证」；探针措辞含「是否符合本项目规范」，**天然诱导去找规范文档**，结果偏乐观（见 F9）。

## 2. 四条验收线判决

### ① 每会话都能看到必须看的东西 —— 🟡 有实证，但只在特定起手姿势下成立

探针 1（评审题，零知情）：子代理第 2 个打开的文件就是 `AGENTS.md`，随后自主走到 `godot-standards.md` → `content-data-conventions.md` → `domain.md` → `CONTEXT.md` → `schema/` → `docs/design/` → `.githooks/pre-commit` → `ci.yml` → 变更镜像表，并正确套用了反模式 lint 正则、过滤字段缺省语义、跨票接缝要求。**判 🟢。**

探针 2（API 默认值题）：答对（4.7 `area_mask` 默认 0；训练记忆会答 1），引用 `godot-standards.md` L110 与镜像表 L334，并主动声明「未联网核证 class reference，以本地记录为准」。**判 🟢。**

两个前提必须同时成立：会话起点在仓库根（看得见 AGENTS.md），且任务性质要求「判断是否符合规范」。F1 与 F9 从两侧削弱它。

### ② 遇问题必做 —— 🟡 机制设计完整，生效链路有断点

机制是全的：`process-audit.md` 有「失守类别 → 反哺动作」映射表；`godot-standards.md` 有硬规则 + 假绿模式 + 核证流程；CI + pre-commit 有机器层（已确认 `.git/config` 中 `core.hookspath=.githooks` 生效，`.githooks/pre-commit` 与 `.github/workflows/ci.yml` 均已入库）。
断点：规则层三天未入库（F1）、元层教训未回流（F3）、反哺链条有「已知未修」实证（F2）。

### ③ 解决后记到该记的地方 —— 记录 🟢 / 落点 🔴

记录侧极强：五天日志沉淀 54 条可辨识教训，逐条带日期与复现细节。落点侧弱：

**「记了」和「记到了该记的地方」是两件事**，这里差 20 个百分点。

## 3. 病灶清单（按严重度）

- **F1 规则层改进卡在工作区未入库。** `audit-runbooks.md` / `content-data-conventions.md` / `toolchain-win.md` 三页 untracked；`AGENTS.md` / `godot-standards.md` / `process-audit.md` 三处改动未提交。`git show HEAD:AGENTS.md` 确认已入库版本**仍是旧版**：不含 Windows 约束、content 约定、拆分后的 process-audit 双页指针。后果：换机 / 新克隆 / CI / 评审者读到的执法体系是三天前的。（本次已解，见 §6。）
- **F2 悬空引用已知未修 = 反哺链条断裂的实证。** `content-data-conventions.md` L25 曾指向一份已随 2026-09-05 回滚删除的存档约定页；09-06 的 AGENTS.md 审查已明确记录这一条，至今未动。（本次已修：该引用改写为「待存档票 #38 重建」，并加机器检查防复发。）连带：09-05 被 `git clean -fd` 删掉的 ADR-0002（存档原子写恢复链）与 `api-4-7-index.json`（39 条 4.5+ 变更快查索引），记忆里写着「已落地」，仓库里零痕迹；存档侧约定（心跳读侧不走恢复链、手改 save.json 五规则）**全部无落点**。
- **F3 元层教训几乎全未回流。** 机制可靠性三层排序、STATUS.md 真相不可评审、文档重排后须 grep 全仓锚点、code-review Spec 轴盲区、Windows 杀毒锁文件型假绿、跨文件改签名 `read_lints` 不报——六条全部只在记忆里。这是「关于机制本身的教训」被系统性漏掉，而它恰恰决定机制能否进化。
- **F4 AGENTS.md 内部自相矛盾。** L48 写「可评审的规则不该只存在于 `.codebuddy/`」，L38 却要求每条 v1 裁量「同时进 `.codebuddy/memory/STATUS.md`」——而这些裁量的真相已在 GitHub 关票评论里。规则自己违反自己。
- **F5 体量倒挂。** 87 KB 不可评审的记忆 vs 31.5 KB 可评审的规则。精简 MEMORY.md（压到 1.8 KB）没有解决问题，只是把体积赶进了日志。
- **F6 「部分回流」成片。** 9 条只落一半：`PackedStringArray` 那条写成了 `pop_back` 变体、`gh api` 数组语法未落、Timer 需 `is_inside_tree()` 未落、掉落层序只在代码注释里。碎片比缺失更难发现。
- **F7 未被任何规则覆盖的高危假绿源。** Windows 对「刚 rename 落盘的文件」立即删 / 改名会间歇失败（杀毒锁文件），零改动重跑即绿——docs 全库零命中，而它的判据（失败点漂移 + 重跑即绿）正是最容易被误判成大面积回归的形态。（本次已补，见 §6。）
- **F8 `schema/` 无消费者。** CI 只在 `game/**` 变更时触发，无 JSON Schema 校验步骤；`AGENTS.md` 无 schema 顶层指针。（已知，待用户拍板。）
- **F9 探针的乐观偏差。** 两题都过了，但题目本身要求「判断是否符合规范」，等于把答案指了一半。真正的高频场景——改一行、加个字段、跑条命令、写份设计稿——不会唤起「我要去找规范文档」这个意图，指针就静默不触发。这是①只能判 🟡 的原因。

## 4. 与既有自审机制的对照

按 `process-audit.md` 的「失守归类 → 反哺映射」表，本次命中三类：

| 失守类别 | 本次实例 | 映射动作是否执行 |
|---|---|---|
| 指针失灵（没走流程） | F1（指针指向未入库页）、F2（悬空引用） | ❌ 已发现未反哺 |
| 语义判断错（合法但次优） | F4（规则自相矛盾）、F5（体量倒挂） | ❌ 未被归类 |
| 机器层漏网（编译过但错） | F2（悬空引用可静态匹配却无检查）、F8（schema 无校验） | ❌ 未扩 lint / CI |

**自身机制要求的动作，在自己的失守上没有执行。** 这不是文档质量问题，是闭环没接通。

## 5. 待拍板建议（按性价比排序，均未执行）

1. **提交规则层**（解 F1）：三页新文档 + 三处改动入库。零成本，立刻让机制对新会话生效。
2. **把「悬空引用检查」变成 CI / 钩子步骤**（解 F2、F6）：静态扫描 Markdown 之间「反引号 / 链接里的 .md 引用目标」是否存在。这正是 F3 里「文档重排后须 grep 锚点」那条未回流教训的机器化形态——**用这套体系自己的方法论，把最痛的那条教训变成判据**。
3. **定 STATUS.md 的定位**（解 F4、F5）：只留当前票 + 上一票 + 指针；v1 裁量的持久真相 = GitHub 关票评论，`AGENTS.md` L38 同步改写，消除自相矛盾。
4. **元层教训回仓**（解 F3）：机制可靠性排序、grep 锚点纪律、code-review Spec 轴盲区，三条进 `process-audit.md` 或新建「机制自守」小节。
5. **skill 化三个高频必做动作**（解 F9）：Godot 核证流程 / 中文落盘通道 / 跨票收尾清单。理由是指针依赖「我要找规范」的意图，skill 由 description 触发，不依赖意图。这一条成本最高，放到前四条之后。
6. **记忆蒸馏机制**（解 F5）：daily 超 30 天蒸馏进 MEMORY.md 后删除；STATUS.md 设条数上限。
7. **补 F7**：Windows 锁文件型假绿进 `godot-standards.md` 假绿模式节。
8. **补 `toolchain-win.md`**：`cmd /c` 里用 `&` 串联多条命令会吞掉前一条带重定向的输出——本次据此一度把「已装机的 `core.hookspath`」误判成未装机。配置 / 状态类查询必须单独一条命令跑。

> **取证纠偏**：审计过程中一度把「`git config --get` 无输出」当作钩子未装机的证据。复核后确认**钩子是装机的**（`.git/config` 有 `core.hookspath=.githooks`），空输出是 `cmd /c` 的 `&` 串联吞输出所致。原判据作废，结论按上条改写——这本身也是一条「查询类结论必须二次确认」的实证。
